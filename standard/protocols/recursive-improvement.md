# Recursive Guidance Improvement

Treat roles, protocols, checklists, presets, schemas, routing, and validation rules as operational infrastructure.

Before changing shared guidance, classify the observed problem as a one-off execution error or a systemic guidance, state-model, ownership, validation, tool, or policy-contradiction gap.

A material guidance candidate should record:

- observed failure pattern and evidence;
- root-cause hypothesis;
- exact target rule or contract;
- proposed change and scope/non-scope;
- expected effect and regression risk;
- validation and falsifier/rollback condition;
- later signal that will show whether it worked.

Prefer consolidation or replacement over policy accretion. Never use recursive improvement to expand top-level authority, cadence, release policy, protected-branch policy, destructive migration authority, or product direction without an explicit higher-level decision.
